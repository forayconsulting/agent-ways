# SPE Loop ways plus an engine `tools:` lane, built with SPE round 1

## Context

The user designed the SPE Loop (Specify, Predict, Evaluate). They run it in Claude Code with a specific mapping:

- The plan mode prompt is a lightweight spec.
- The approved plan is the prediction.
- Executing the plan as a dynamic Workflow is the eval.
- The user re-enters plan mode, and Claude respecs for the next round.

They want agent ways that sustain and steer this loop, because it can run for a long time without supervision. They also want the ways guidance to arrive at the moment of each loop step: when plan mode is entered, when the plan is approved, and when a Workflow launches.

These hooks must extend the agent-ways engine so the work can go upstream to aaronsb/agent-ways. User-only shortcut scripts are not acceptable.

The work itself runs as SPE round 1:
- The user's prompt is the round 1 spec.
- This plan is the round 1 prediction.
- The Workflow run after approval is the round 1 eval.

- `~/Downloads/SPE-for-Practitioners.pdf` (16 pp, 2026-10-17)
- `~/Downloads/Specify, Predict, Evaluate.pdf` (4 pp)
- `~/Desktop/quantum/spe/`, its git history, and the transcript `~/.claude/projects/-Users-claytonchancey-Desktop-quantum/4ec7cf7f-....jsonl`. That project ran rounds r01 to r03 on 2026-10-21.

Honest limits:
- The engine has no lane for tool names today. `ways hook` events are prompt, state, command, file, task, post-tool, pull, queued, stop, subagent-start, session-start, and tasks-active.
- Whether Claude Code fires PreToolUse and PostToolUse for `EnterPlanMode`, `ExitPlanMode`, and `Workflow`, and what their `tool_input` holds, is unverified. Step 3 probes it first.
- `EnterPlanMode` fires only when Claude enters plan mode itself. When the user toggles plan mode with Shift+Tab, no tool call happens. The prompt pattern covers that case.
- The live binary (`ways 1.39.7`, live clone at e5aa96a4, dirty) will not have the new lane until the user updates the live install. That is a separate, gated step.
- The semantic lane is off on this machine ("Calibration: MISSING").

## Decisions (confirmed with the user, 2026-10-21)

1. **Commits:** local commits per SPE step (`SPE r01 specify|predict|evaluate (harness|results)|learn: ...`) and the tag `spe-r01`. No push.
2. **Scale:** a large eval. The user said "Go big or go home!"
3. **Hooks extend the agent-ways engine** (a new frontmatter lane plus the shipped `settings.json` matcher), so they can be PR'd upstream. No user-only hook scripts.
4. **Location:** the tree lives in the repo for upstream and is also installed in personal ways so it fires live.

## Defaults adopted (override if wrong)

- **Base and branch.** The user first picked "new branch from feat/eval-ways". That branch sits on an old upstream commit (#766) that lacks the code an engine PR must target. So the work goes on `feat/spe-loop-way`, cut from fresh `origin/main` after `git fetch origin`. It uses a git worktree at `~/Desktop/praecipio_agent_ways-spe`. The current checkout and its uncommitted eval-ways edits stay untouched.
- **Way id is `evaluative/spe`.** Upstream already has `evaluative/` (forecast, model-oracle, ablation), and it is live. The personal copy uses the same id at `~/.config/agent-ways/ways/evaluative/spe/`. That way it shadows cleanly, and it can be deleted once upstream ships it.
- **The field name is `tools:`.** It matches `commands:` and `files:`, the plural noun of the thing matched. The ADR notes the clash with agent definitions' `tools:`. The reviewer can rename it.
- **Phase.** A second field, `tool_phase: pre|post|both`, defaults to `pre`. Post skips `PostToolUseFailure`, per ADR-188 item 2.
- **Shipped matcher list.** The shipped `settings.json` gets a fixed matcher `EnterPlanMode|ExitPlanMode|Workflow` for both PreToolUse and PostToolUse. It is not `.*`, which would spawn the binary on every tool call. Extending the list is a documented one-line template change.
- **Models.** Trial workers and judges run on Opus 5.5, never Haiku. Code grading runs in the main loop with Python.
- **Install order.** Nothing is installed under `~/.config/agent-ways` until the eval has run. Installing earlier would let the way leak into config A through `subagent-brief.sh`.

## Round 1 Predict (this plan is the prediction)

### A. Engine change: the `tools:` lane

- **Frontmatter:**
  - `tools: <regex>` is matched case-insensitively against `tool_name`, using `compile_trigger` and `regex_span`.
  - `tool_phase: pre|post|both` defaults to `pre`.
  - `tools:` is fire-bearing, so it needs `refire:`. It works with `scope:` and `when:` like the other lanes.
- **Code, mirroring the file lane:**
  - `HookEvent::Tool` plus `Request::Tool { session, tool, phase }`, from `/tool_name` and `/hook_event_name`. `PostToolUseFailure` maps to Skip.
  - `scan::tool()` emits with channel `"tool"` and `hookEventName` set to the real event.
  - Add the `"tool"` channel in `subagent_lane()`, and add `tools` and `tool_phase` to `WayCandidate` and `parse_candidate()`.
  - Add `"tools"` to `FIRE_BEARING_FIELDS`, and update the no-firing-path warning text.
  - Surface the fields in `introspection::MatchCriteria`, `introspect/why.rs`, the settings TUI field list, and the `init.rs` table.
- **Wiring:**
  - `hooks/ways/check-tool.sh` (two lines, `ways_hook tool`)
  - `settings.json` gets PreToolUse and PostToolUse entries with matcher `EnterPlanMode|ExitPlanMode|Workflow`, each in its own entry
  - Schema: `tools` and `tool_phase` go under `way.trigger`, `file_exists` goes under the way `when:` block, and the header contract lane list is updated
- **Tests:**
  - `input.rs` unit tests, including `tool_needs_a_name` and `post_failure_is_skipped`
  - `scan` unit tests for the regex and phase filter
  - A `per_file.rs` firing-path test
  - A `session_sim.rs` scenario for tool triggers: a fixture `testdomain/tool-trigger/tool-trigger.md` and raw payloads through `ways hook tool`. It asserts the envelope for pre and post, the phase filter, the `when: file_exists` gate, and a refire in a second round in the same session.
  - A `hooks-test.sh` case
  - A `SIMULATION-SPEC.md` row
- **Docs:** ADR-704 "Tool-name trigger lane". Edit the lane lists in `docs/architecture.md`, `docs/hooks-and-ways/{README,matching,extending,engine-reference}.md`, `docs/reference/events.md`, `README.md`, and the `meta/knowledge/authoring` ways.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Claude Code does not fire hooks for one of the tools | The step 3 probe runs before the engine work. The lane stays generic. Any tool that fails is dropped from the shipped matcher and logged |
| A build disturbs the live binary | Build only in the worktree. Never run `make dev-install`. Step 11 is gated |
| Ceiling effect | Strict pass rule. The T6 trap. A real baseline in A |
| Workers read the answer keys | No-tools instruction. `peek.py` voids trials that peek |
| The judge shares the worker's model family | Code checks carry the pass rule. The limit is disclosed in the log |
| The ways leak into config A | The ways are installed only at step 10 |
| The reviewer objects to the `tools:` name | The ADR lists alternatives (`tool_names:`, `on_tools:`). The rename is mechanical |
